# MY LIFE — Post-V1 회원 정보 관리 계획

Status: `PROPOSAL — NOT IMPLEMENTED`

작성 기준: 2026-10-05. 사용자 요청으로 후속 설계에 추가합니다. V1에는 회원가입, 서버, user table, 로그인 화면을 추가하지 않습니다. 아래 제안은 구현 전 승인할 대상입니다.

## 1. 목적과 경계

- 로그인 없이도 현재의 로컬 기록 기능을 계속 사용합니다.
- 회원 기능의 목적은 선택적 Cloud 서비스, 기기 간 본인 확인, 구독 권한 관리입니다. 광고 타깃용 개인 정보 수집을 목적으로 하지 않습니다.
- 회원가입만으로 기록을 서버로 보내지 않습니다. 로그인, 백업, Cloud Sync 동의는 별개입니다.
- 프로필 정보와 Memo/Expense/Photo 원문은 분리합니다.

## 2. 최소 회원 기능 제안

1. 가입/로그인: 검증된 인증 제공자 SDK 사용. 직접 비밀번호 저장/인증 서버 구현은 지양합니다.
2. 프로필: 선택적 표시 이름, 언어. 이메일은 인증 방식에서 필요한 경우만 처리하고 주소·생년월일·성별·카드 정보는 기본 수집하지 않습니다.
3. 연결된 로그인 수단 확인/연결 해제: 본인 재확인과 마지막 로그인 수단 보호.
4. 로그아웃/세션 만료/기기 세션 철회.
5. 개인정보 동의 이력과 회원 탈퇴/데이터 삭제 요청.
6. 구독 상태, 구매 복원과 구독 관리 경로. 탈퇴와 스토어 구독 취소는 별도 작업임을 안내합니다.

Apple/Google 로그인 또는 이메일 방식 중 무엇을 제공할지, 인증 제공자, 최소 이용 연령, 출시 국가는 아직 미결정입니다. iOS의 로그인 제공 조건은 구현 시 Apple 정책을 다시 확인합니다.

## 3. 개념 데이터 모델 — 서버 구현 전 검토용

| 개념 | 최소 데이터 | 경계 |
| --- | --- | --- |
| Account | 내부 UUID, 상태, 생성/삭제 요청 시각 | Record와 별도 |
| AuthIdentity | Account FK, provider, provider subject | provider/subject UNIQUE, 인증 공급자에서 검증 |
| Profile | Account FK, 선택적 표시 이름, 언어 | 원문/사진 없음 |
| Consent | Account FK, 동의 유형·문서 버전·시각·철회 시각 | 서비스/마케팅/Cloud 별도 |
| Entitlement | Account FK, 상품, 상태, 유효 기간 | 클라이언트 flag로 유료 권한 결정 금지 |
| DeletionRequest | Account FK, 처리 단계·요청/완료 시각 | 개인정보 원문 없는 운영 이력 |

실제 SQL schema, retention 기간과 migration은 아직 확정하지 않습니다. 법령상 보존이 필요한 데이터는 국가·운영 형태를 정한 뒤 전문가 검토를 받아 별도 정책으로 정의합니다.

## 4. 로컬 데이터 소유권 — 구현의 선행 결정

```text
로컬 기록 → 사용자의 명시적 연결 승인 → 특정 Account의 공간
```

- 기존 Record UUID는 유지합니다. 로그인 여부에 따라 기존 PK를 교체하지 않습니다.
- 제안: 기기의 기존 로컬 공간은 한 Account에만 명시적으로 연결합니다. 다른 계정 로그인 시 기존 계정 공간을 보여주거나 자동 업로드하지 않습니다.
- 로그아웃으로 기기 기록을 자동 삭제하지 않습니다. 남길지/지울지는 별도 UX와 재확인으로 결정합니다.
- 계정 전환 시 공간 분리, guest 기록의 최초 연결, Cloud 데이터와의 중복/충돌 정책을 정하기 전 계정 전환과 sync를 구현하지 않습니다.
- 회원 탈퇴에서 서버 삭제, 로컬 사본 처리, 구매 상태, OS 캘린더 원본 보존을 각각 안내합니다.

## 5. 보안과 삭제

- 인증 토큰은 OS 보호 저장소에 보관하는 방안을 검토합니다. SQLite/일반 preferences에 비밀번호나 refresh token을 저장하지 않습니다.
- 회원별 서버 접근 제어와 다른 회원의 기록 접근 차단 테스트가 필수입니다.
- 사진 접근 URL, 토큰, 이메일과 결제 원문을 로그에 남기지 않습니다.
- 삭제는 재인증 → 영향 설명 → 명시적 요청 → 서버 접근 철회 → 데이터 처리 → 완료 안내로 설계합니다. 임의의 운영자 삭제 기능은 넣지 않습니다.
- Apple은 계정 생성 앱의 앱 내 삭제 시작 경로를 요구합니다. [Apple 계정 삭제 안내](https://developer.apple.com/support/offering-account-deletion-in-your-app/)
- Google Play는 해당 계정 앱에 앱 내 삭제 경로와 앱 밖의 웹 삭제 요청 경로를 요구합니다. [Google 계정 삭제 정책](https://support.google.com/googleplay/android-developer/answer/13327111?hl=en)

위 정책 요약은 구현 시 재확인해야 합니다. 개인정보처리방침, 운영자 정보·연락처, 동의 문구는 실제 운영 주체/데이터 흐름 확정 후 공개합니다.

## 6. 구현 순서와 승인 항목

1. V1 실기기 검증·안정화 완료.
2. 수동 Backup/Restore와 데이터 이동 수단 설계/검증 (기존 문서의 선행 순서 유지).
3. 운영 주체, 출시 국가, 인증 제공자, 로그인 방식과 데이터 소유권 승인.
4. 회원 관리와 삭제 UX 구현/테스트. 로그인만 도입하고 자동 업로드하지 않음.
5. 선택적 Cloud Sync를 별도 승인 후 구현.
6. 수익화 상품/권한과 구매 복원 연결.

완료 기준: guest 기능 유지, 계정 간 격리, 로그아웃 후 보존 정책, 동의 철회, 앱/웹 삭제 요청과 오류 재시도, 개인정보 처리 문서와 실제 코드 일치.
